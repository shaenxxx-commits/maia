## АРХИТЕКТУРА

### OpenClaw — не подключать к ядру через MCP
Решение: внешние агенты потребляют сигнал через Telegram или
read-only endpoint. К ядру не подключаются.
Почему: физическая изоляция важнее интеграции. Риск prompt
injection и широких разрешений неприемлем.
Откат: изолированный read-only endpoint при появлении реального кейса.
Дата: 2026-05-17

### n8n — слой реакций, не отдельный агент
Решение: рутинные реакции на сигнал — через n8n workflow.
Почему: I13. Не строить то что уже работает.
Дата: 2026-05-17

### Рой агентов — через внешние API, не через MCP внутрь ядра
Решение: внешние агенты подключаются как к источнику истины через
контролируемый endpoint, не к ядру напрямую.
Почему: безопасность, изоляция ядра.
Дата: 2026-05-17

### n8n Schedule Trigger (hours-интервал) — воспроизводимый баг
Решение: зафиксировано как известное поведение, не как
исправление — фикс не применялся. Hours-интервальные Schedule
Trigger (cs.AI, cs.LG, GitHub Trending — hoursInterval=2) не
переустанавливают таймер после первого срабатывания при старте
процесса n8n — замолкают до явного рестарта контейнера. Minutes-
интервал (HackerNews, 30 мин) этой проблеме не подвержен.
Почему не чинится немедленно: воспроизведено дважды подряд на
разных рестартах хоста (20.09, 21-22.09), но система каждый раз
самовосстанавливается — см. решение "watchdog.sh — реально
автоматически поднимает контейнеры" ниже. Каждый такой рестарт
контейнера (вызванный watchdog при падении любого из 4 основных
контейнеров) параллельно чинит и застрявший schedule.
Откат: если проблема станет мешать чаще, чем происходят рестарты
контейнеров — потребуется отдельный фикс (например, принудительный
рестарт только n8n по расписанию) или апстрим-issue в n8n.
Дата: 2026-09-21/22

### watchdog.sh — реально автоматически поднимает контейнеры
(исправление неточной записи в RUNTIME.md)
Решение: зафиксирован факт — systemd-таймер maia-watchdog.timer
запускает maia-watchdog.service каждые 5 минут независимо от
того, что сам .service формально помечен "disabled" (это значит
только "не стартует при загрузке хоста", не "не работает вообще").
Watchdog при обнаружении упавшего контейнера (status != running)
выполняет `docker compose up -d --no-deps <name>` автоматически,
без участия Архитектора.
Почему это решение, а не просто наблюдение: прежняя формулировка
в RUNTIME.md ("Restart policy = 'no'... требуется ручной cold
start") вводила в заблуждение — технически верно про Docker restart
policy, но не отражала, что watchdog компенсирует это полностью.
Подтверждено прямым логом (journalctl, 22.09.2026): рестарт хоста
09:17-09:18 UTC — watchdog за 43 секунды последовательно поднял
все 4 контейнера (maia-db→maia-core-v2→maia-forwarder→n8n),
задержка между полным падением и восстановлением — не более
5-10 минут (интервал таймера + grace period 180с на cold start).
Откат: н/д — это фактическая правка неточности в документации,
не решение об изменении поведения системы.
Дата: 2026-09-22

### S2 (Semantic Scholar) → OpenAlex — замена enrichment-источника
Решение: Semantic Scholar заменён на OpenAlex как источник
обогащения entity-слоя (citation_count, venue и т.д.).
Почему: S2 требует одобрения формы для production-лимита без
ключа — 100 запросов/5 минут. Форма отклоняет client-side все
крупные бесплатные email-провайдеры (подтверждено 4/4: gmail,
outlook, protonmail, icloud). Покупка отдельного домена
рассматривалась как обход — проверка показала, что даже пройдя
client-side фильтр, итоговое одобрение формы (возможен ручной
review на институциональность) не гарантировано ничем публично
подтверждённым. OpenAlex не требует ключа/формы/одобрения вообще:
100 000 запросов/день, 10 req/sec — подтверждено официальной
документацией (docsold.openalex.org), не только заявлено в промо.
Сравнение по цифрам: S2 без ключа — 100 запросов/5 минут
(≈28800/день теоретически, но непредсказуемо под нагрузкой);
OpenAlex — 100 000/день без всякой регистрации. Покрытие сопоставимо
(214M vs 250M работ). Теряется: TLDR (авто-резюме от S2) — не
критично, LLM интерпретирует содержание сам.
Урок, зафиксированный явно: перед закладыванием внешнего API как
архитектурной зависимости — проверять доступ эмпирически (пробный
запрос), не полагаться на документацию/предположение о доступности
для конкретного случая использования. Тот же класс ошибки, что уже
случался в проекте (предположения без проверки терминалом).
Откат: н/д — OpenAlex не создаёт новых зависимостей/затрат,
пересмотр не предвидится без веской причины.
Дата: 2026-09-21 (решение Архитектора после research-вектора)

### Entity-слой (Шаг 3) — первая реализация
Решение: таблица paper_entities создана (paper_id PK, arxiv_id
мягкая связь без FK — БД проекта архитектурно не имеет ни одного
FK, решение вводить первый FK явно отклонено на этой стадии).
Поля: title, cited_by_count, venue, first_seen_at, enriched_at.
influential_citation_count — НЕ создавалось полем: подтверждено
отсутствие такого поля в OpenAlex вообще (живыми тестами).
Метод точного matching: GET /works?filter=doi:https://doi.org/
10.48550/arxiv.{ID}&mailto={email} — строгий формат обязателен
(полный DOI URL, строчные arxiv). Title-based поиск ПРИЗНАН
НЕНАДЁЖНЫМ: тест на "Attention Is All You Need" вернул испорченную
дубль-запись (год 2025 вместо 2017, подозрительный DOI) на первом
месте — известная в сообществе OpenAlex проблема дублей/merge-
записей. Matching — только через DOI, построенный из уже
известного arxiv_id, никогда через текстовый поиск.
Первая живая end-to-end запись (реальный сигнал → OpenAlex →
paper_entities) — ОТЛОЖЕНА объективно, не по вине метода: все
статьи текущего потока (с 21.09, после TRUNCATE) младше
минимального возраста индексации OpenAlex (7-14 дней). Решение —
НЕ форсировать тестовой заменой на статью вне потока MAIA, ждать
естественного созревания (~начало-середина октября 2026).
Откат: н/д — таблица создана, логика проверена по частям, ждёт
данных, не пересмотра.
Дата: 2026-09-21/22

### Проверка execution log n8n — сверка input/output обязательна
Решение: при read-only диагностике execution в n8n — не полагаться
на статус "success" в общем списке execution как признак реального
срабатывания ноды.
Почему: disabled-нода работает как pass-through, отображается со
статусом success — ложное впечатление реального выполнения.
Найдено на практике: ложная тревога по tg-001 (14.09.2026).
Дата: 2026-09-14

### Внешний API как архитектурная зависимость — проверять эмпирически
Решение: перед тем как закладывать внешний сервис/API в план как
опору для будущей работы — делать пробный запрос/регистрацию, не
полагаться на документацию или общие предположения о доступности.
Почему: план изначально строился на S2 ("бесплатный, 100 req/sec"
по документации) без учёта, что повышенный лимит требует одобрения
формы, которая на практике блокирует основные бесплатные email-
провайдеры. Обнаружено только при попытке реализации, не на
этапе планирования. Тот же класс ошибки, что уже случался в
проекте (архитектурные решения на предположениях, не проверенные
терминалом).
Дата: 2026-09-21

### Сравнение отчётов РЧ vs пересказ УЧ — иерархия подтверждена,
точечная корректировка внесена
Решение: проведена серия из пяти прямых сравнений отчёт РЧ "как
есть" vs тот же материал через УЧ. Искажений смысла/фактов не
найдено ни разу. Систематическая находка — потеря операционной
конкретики (точные числа, execution ID, конкретные форматы ошибок)
в пользу обобщённых формулировок при пересказе УЧ. Контрпример в
обратном направлении (УЧ→РЧ, постановка задачи): УЧ один раз
добавил инженерную структуру, не терял её.
Решение: трёхуровневая иерархия КОНЦЕПТ→УЧ→РЧ сохраняется без
структурных изменений. Правило для УЧ (передавать конкретные
технические находки дословно/близко к тексту) внесено в
PROMPTS_CHAT_LAUNCH.md v3.6.
Дата: 2026-09-22
