## АРХИТЕКТУРА

### OpenClaw — не подключать к ядру через MCP
Решение: внешние агенты потребляют сигнал через Telegram или
read-only endpoint. К ядру не подключаются.
Почему: физическая изоляция важнее интеграции. Риск prompt
injection и широких разрешений неприемлем.
Откат: изолированный read-only endpoint при появлении реального кейса.
Дата: 2026-05-17

### n8n — слой реакций, не отдельный агент
Решение: рутинные реакции на сигнал — через n8n workflow.
Почему: I13. Не строить то что уже работает.
Дата: 2026-05-17

### Рой агентов — через внешние API, не через MCP внутрь ядра
Решение: внешние агенты подключаются как к источнику истины через
контролируемый endpoint, не к ядру напрямую.
Почему: безопасность, изоляция ядра.
Дата: 2026-05-17

### DDA — Documentation-Driven Architecture
Решение: документация определяет систему, не описывает её.
Сервер = источник истины. Projects = синхронизированные копии.
Git = история.
Почему: масштабирование Архитектора через документацию.
Дата: 2026-05-31
Ревью: после завершения TRANSITION.md Шага 6

### watchdog — инцидент 27.09: порча .env остановила автоподъём
Решение: зафиксирован факт сбоя и его причина, не новая политика.
Первая строка .env содержала слитую без разделителя команду nano
с существующей переменной POSTGRES_PASSWORD (следствие правки .env
в рамках ротации ключей I7, 25.09-27.09). watchdog.sh делает
`source "$ENV_FILE"`, bash исполнял эту строку как команду, nano
падал под systemd (no TTY), set -euo pipefail обрывал весь скрипт
до docker-вызовов — ни один контейнер не поднимался автоматически.
Причина установлена: 7-шаговая верификация (journalctl, исключение
альтернативных причин, трассировка bash -x, подтверждение фиксом).
Фикс: sed-правка строки, верификация source и полного прогона в
no-TTY, финальная верификация реальным systemctl start.
Пароль частично засветился в трассировке дважды за сессию — оценено
как не компрометация, ротация не требуется (решение Архитектора).
Новое правило: после любой ручной правки .env — обязательная
проверка (`bash -n .env` или безопасный `source`) перед тем, как
считать задачу закрытой.
Дата: 2026-09-27

### "1 из 5" — потеря 80% результатов LLM, переплата за вызовы
Нода Parse and Build SQL в Analyzer была написана под поэлементный
вызов, но запускалась один раз на батч из 5 items от OpenRouter —
обрабатывался только первый item, 4 терялись молча. LLM оплачивался
за все 5 вызовов.
Фикс: цикл по всем items, id-привязка сохранена, return массива из 5
записей. Подтверждено живым запуском (PG Update result обрабатывает
5 items за цикл).
Семантика пустого content изменена: ранее попадание пустого ответа
в единственный обрабатываемый item приводило к status='irrelevant',
score=0 — то есть сбой парсинга молча маскировался под суждение о
содержании. Решение: пустой/непарсящийся content НЕ помечается
irrelevant — оставляется для повторной попытки, при исчерпании
попыток получает отдельный статус (не искажающий статистику
релевантности).
Дата: 2026-10-01/02

### 43% оценённых строк были искажены сбоем парсинга (758 из 1771)
Разбор по типам: 306 пустой content, 233 рассуждение вместо JSON,
171 обрезанный ответ, 22 неожиданный конец JSON, 16 незакавыченное
свойство. Корневая причина основной доли — max_tokens=500 при
reasoning-модели (nemotron-3-super тратила лимит на рассуждение,
content оставался пустым/обрезанным).
Фикс: max_tokens поднят до 1500 (бесплатно по квоте — она считается
в запросах, не в токенах).
Переоценка: 329 строк (758 на момент диагностики, часть уже закрылась
фиксом "1 из 5") пересчитаны одноразовым скриптом, UPDATE по
конкретным id (status + meta.groq), порциями 50+100+179, 0 провалов.
Маркер meta.groq.rescored='2026-10-02' оставлен для отслеживания.
⚠️ Процедурное отступление: бэкап таблицы перед этим UPDATE не
делался (правило "бэкап перед любой правкой" держалось весь аудит
до этого шага). I1/I2 не нарушены (UPDATE по id, не DELETE), но
отмечается как единичное отклонение, не норма.
После фикса score_failed в живом потоке = 0 (подтверждено).
Дата: 2026-10-02
