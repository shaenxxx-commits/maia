### S2 → OpenAlex — замена enrichment-источника (21.09.2026)
Semantic Scholar заменён на OpenAlex как источник обогащения
для entity-слоя. Причина: S2 требует одобрения формы для
production-лимита, форма client-side блокирует все крупные
бесплатные email-провайдеры (подтверждено 4/4: gmail, outlook,
protonmail, icloud). Покупка домена рассматривалась как обход —
при проверке выяснилось, что даже пройдя client-side фильтр,
итоговое одобрение формы не гарантировано (нет публичного
подтверждения ни в одну, ни в другую сторону про "институциональность").
OpenAlex — без ключа, без формы, без одобрения: 100 000 запросов/
день, 10 req/sec, подтверждено официальной документацией
(docsold.openalex.org). Email в mailto-параметре — не барьер,
просто "вежливая идентификация" для более быстрого пула.
Урок, зафиксированный явно: перед закладыванием внешнего API как
архитектурной зависимости — проверять доступ эмпирически (пробный
запрос), не полагаться на документацию/предположение о доступности
для конкретного случая использования.

### Entity-слой — первая реализация (21-22.09.2026)
Таблица paper_entities создана (paper_id PK, arxiv_id мягкая связь
без FK — решение сохранено, БД в проекте архитектурно не имеет
ни одного FK). Маппинг полей OpenAlex подтверждён живыми данными:
cited_by_count (прямое совпадение), venue → primary_location.
source.display_name. influential_citation_count — подтверждено
отсутствие такого поля в OpenAlex, колонка не создавалась.
Метод точного поиска: GET /works?filter=doi:https://doi.org/
10.48550/arxiv.{ID}&mailto={email} — строгий формат обязателен
(полный DOI URL, строчные arxiv; bare DOI и прямой /works/doi:
lookup не работают). Title-based поиск ПРИЗНАН НЕНАДЁЖНЫМ для
entity-matching — известная проблема дублей/испорченных merge-
записей в OpenAlex (пример: "Attention Is All You Need" вернул
дубль с годом 2025 вместо 2017 на первом месте при поиске по
названию). Matching — только через DOI, построенный из известного
arxiv_id.
Первая полная end-to-end запись (реальный сигнал MAIA → OpenAlex →
paper_entities) — ОТЛОЖЕНА. Причина объективная, не техническая:
все статьи текущего потока (начался 21.09, после TRUNCATE)
опубликованы 21.09 — OpenAlex их ещё не проиндексировал (ожидание
7-14 дней согласно ожиданиям самого плана). Открытие вектора
ожидается ~начало-середина октября 2026, когда статьи наберут
возраст. НЕ форсировать тестовой заменой на произвольную
публичную статью вне потока MAIA — решение принято явно, чтобы
не подменять "реальный сигнал" искусственным ради галочки.
Новый ресурс проекта: email maia.systems@proton.me (ProtonMail,
бесплатный), .env: MAIA_EMAIL. Изначально создан под S2, остался
и используется для OpenAlex mailto + общие внешние формы/API
проекта (I7 — не личная почта Архитектора). Зафиксирован в
resource_ledger (id=10, type=access).

### Диагностические находки (21-22.09.2026)

n8n schedule-trigger баг: hours-интервальные Schedule Trigger
(cs.AI, cs.LG, github_trending — все hoursInterval=2) не
самовосстанавливаются после cold start процесса n8n без явного
рестарта контейнера. Подтверждено дважды подряд на разных
рестартах хоста. minutes-интервал (hackernews) не подвержен.
Естественно устраняется при следующем рестарте n8n — не требует
отдельного немедленного фикса.

watchdog.sh — РЕАЛЬНО автоматически поднимает упавшие контейнеры
(systemd timer, каждые 5 минут, ExecStart в maia-watchdog.service,
хотя сам сервис формально помечен "disabled" — это означает
только "не стартует сам при загрузке хоста", таймер работает
независимо). RUNTIME.md ДО ЭТОЙ СЕССИИ содержал неточную
формулировку "требуется ручной cold start" — исправлено. Реальное
время восстановления системы после рестарта хоста — ~5-10 минут,
не "вручную, когда вспомнит Архитектор". Подтверждено прямым
логом (journalctl) с точными ALERT/OK записями и содержимым
самого watchdog.sh.

⚠️ arxiv_cs_lg — ПОЛНОСТЬЮ НЕФУНКЦИОНАЛЕН, не частично. За весь
батч 21.09 — 0 строк любого статуса (не только с апострофами, как
считалось раньше по находке от 19.09). SQL-баг в узле "PG Insert"
(конкатенация без экранирования) — известная причина, но охват
проблемы оказался шире предполагаемого. ПРИОРИТЕТНАЯ находка для
следующей технической сессии — не общий backlog наравне с
остальным.

Известный, не расследованный сопутствующий факт: LibreChat снова
замечен в статусе "Restarting" (было "остановлен вручную 14.09"
из-за DNS crash-loop) — не исследовалось в рамках этой сессии,
требует отдельной проверки при следующем техническом векторе.

## МЕТОДОЛОГИЧЕСКИЙ ЭКСПЕРИМЕНТ — РЕЗУЛЬТАТ

По инициативе Архитектора проведена серия прямых сравнений:
отчёт РЧ "как есть" vs тот же материал, пройденный через УЧ,
на пяти независимых парах за сессию. Цель — проверить, не
искажает/не теряет ли промежуточный слой УЧ информацию, и
осмысленно оценить необходимость трёхуровневой иерархии.

Результат: искажений смысла или фактов не найдено ни в одном
случае. Систематическая находка — потеря операционной конкретики
(точные числа, execution ID, конкретные проверенные и
опровергнутые варианты, точные форматы ошибок) в пользу более
общих формулировок при пересказе УЧ. Один контрпример в обратную
сторону: в направлении УЧ→РЧ (постановка задачи, не отчёт наверх)
УЧ один раз добавил инженерную ценность (структурировал порядок
диагностики, предвосхитил вопрос по I2), не терял её.

Решение: иерархия КОНЦЕПТ→УЧ→РЧ сохраняется без изменений в
структуре. Точечная корректировка внесена в PROMPTS_CHAT_LAUNCH.md
(v3.6) — правило для УЧ передавать конкретные технические находки
РЧ дословно/близко к тексту, не пересказывать обобщённо.
